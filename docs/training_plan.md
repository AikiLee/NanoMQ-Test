# 训练项目体系：渐进式思想渗透

共 4 个阶段，12 个项目。从单进程到分布式，从确定性到不确定性，从"能跑"到"能证明正确"。

---

## 阶段一：计算思维的底层训练（单线程、确定性、可证明）

---

### 项目 1：事件驱动的状态机框架 + 红绿灯模拟

**难度：** ⭐☆☆☆☆ | **周期：** 1 周

**需求：**
实现一个通用的事件驱动状态机框架（不是只解决红绿灯这一种状态机），然后用它模拟一个十字路口红绿灯系统。路口还要有行人按钮——行人按下后，当前周期结束后插入一个全红+行人通行阶段。

**框架要求：**
- 定义状态、事件、转移规则——转移规则是 `(当前状态, 事件) → (目标状态, 副作用函数)`
- 框架和具体业务逻辑分离
- 非法转移（某个状态下收到不该收到的事件）必须报错
- 能打印状态转移的 trace 日志

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **状态机** | 亲手实现框架——你会在未来项目中反复用到这个模式 |
| **关注点分离** | 框架（何时转移）和业务（转移时做什么）的边界 |
| **Fail-fast** | 非法转移立刻报错——状态机最重要的约束 |
| **测试：契约 + 等价类** | 每个状态对每类事件的响应是等价类；测试所有非法转移 |

**验收：**
- 正常周期：绿→黄→红 循环
- 行人按钮触发后正确插入全红阶段
- 在红灯时按行人按钮不生效（非法事件被拦截报错）
- 框架可以不经修改用于下一个项目

### 项目 2：正则表达式引擎（NFA 实现）

**难度：** ⭐⭐☆☆☆ | **周期：** 1.5 周

**需求：**
实现一个支持 `|`、`*`、`+`、`?`、`()`、`.` 的正则匹配引擎。用 Thompson NFA 构造法，**不用回溯**。

**要求：**
- 从正则字符串构建 NFA（状态 + epsilon 转移的图）
- 用多状态同时模拟的方式执行匹配（非确定性→确定性的运行时转换）
- 能对匹配失败给出位置报告

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **状态机（非确定性）** | NFA 是状态机的高阶形态——同一时刻处于多个状态 |
| **数据流（管线）** | 词法→语法树→NFA→模拟器，四阶段管线 |
| **分治** | 复合正则的结构就是递归分治 |
| **惰性/贪心** | 理解 `*` 的匹配语义——为什么 NFA 天然非贪心 |
| **测试：属性测试** | 找 100 个随机正则在你的引擎和标准库之间交叉验证 |

**为什么放在第二个：** 正则引擎会彻底刷新你对"程序"的认知——代码不再只是一串指令，而是一个有状态的图在输入上行走。

### 项目 3：WAL + 故障恢复的迷你数据库

**难度：** ⭐⭐☆☆☆ | **周期：** 1.5 周

**需求：**
实现一个简单的持久化 KV 存储。内存中维护一个有序 map（跳表），所有写操作先追加到 WAL 文件，再更新内存。

**关键约束：**
- 进程在任何位置 crash——WAL 的 fsync 策略是你需要思考的
- 启动时重放 WAL 恢复到 crash 前状态
- 实现 checkpoint（快照当前内存状态到文件 + 截断 WAL）
- 需要你自己考虑并发访问时 WAL 写的顺序性

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **容错：幂等** | WAL 重放必须是幂等的——重放一半 crash 怎么办？ |
| **持久化 = 顺序写** | 为什么 WAL 快？为什么不是直接写数据文件？ |
| **超时/退避（fsync 策略）** | 每次写都 fsync？还是 batch？性能和安全的 tradeoff |
| **数据流** | 写操作在内存、WAL、checkpoint 三条路径上的流动 |
| **测试：Crash 注入** | 在随机位置 kill 进程然后验证数据完整性 |

## 阶段二：并发与正确性（多线程、非确定性、可推理）

### 项目 4：无锁并发队列 + 验证工具

**难度：** ⭐⭐⭐☆☆ | **周期：** 2 周

**需求：**
实现一个 MPSC（多生产者单消费者）无锁队列。不能使用 mutex。

**逐步要求：**
1. 先实现单消费者单生产者的 lock-free 环形缓冲（只用原子操作 + CAS）
2. 扩展到多生产者——用 CAS 竞争槽位
3. 写一个并发测试工具，跑 1000 万次 push/pop，验证：
   - 没有数据丢失
   - 没有重复
   - 顺序是否符合 FIFO（多生产者情况下你能保证什么级别的 FIFO？）

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **共享内存 + CAS** | 无锁编程的核心原语——比锁更低层的并发 |
| **内存模型** | memory_order_acquire/release 的语义和位置 |
| **并发 vs 并行** | 单核上的 lock-free 和多核上的 lock-free 有什么不同？ |
| **ABA 问题** | CAS 的经典陷阱——怎么解决？ |
| **测试：属性 + 压力** | 不是测某个具体值，而是测"所有元素都出现了且没有多" |

**这个项目的价值：** 你理解了无锁之后，用锁的时候就知道"锁到底在替我做什么"，不再把锁当玄学。

### 项目 5：线程安全的 B+ 树索引

**难度：** ⭐⭐⭐☆☆ | **周期：** 2 周

**需求：**
在内存中实现 B+ 树（只存内存，不写磁盘），支持并发读写。

**要求：**
- 实现 B+ 树的基本操作：insert、search、range_scan
- 用 latch crabbing 协议做并发控制（读时持父节点 latch，写时预持沿途 latch）
- 支持读写并发——读不阻塞读，读尽可能少阻塞写
- 实现迭代器——在并发修改下迭代器怎么保证一致性？

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **锁的粒度** | 全树锁→节点锁→latch crabbing，体会粒度对吞吐的影响 |
| **死锁预防** | 为什么 latch crabbing 按从上到下加锁不会死锁？ |
| **数据结构选择** | 为什么数据库用 B+ 而不用红黑树？IO 模型的影响 |
| **封装** | B+ 树的内部结构对调用者完全不可见 |
| **测试：等价类** | 空树、单节点、分裂、合并的每种情况 |

### 项目 6：轻量级协程库

**难度：** ⭐⭐⭐⭐☆ | **周期：** 2 周

**需求：**
实现一个用户态协程库。核心是"有栈协程"——每个协程有自己的栈，可以随时 suspend 和 resume。

**要求：**
- 实现上下文切换（保存/恢复寄存器和栈指针）
- 实现调度器：就绪队列、阻塞队列、定时器轮询
- 协程 yield 时回到调度器，调度器选下一个就绪协程
- 实现 channel（类似 Go 的 chan），无缓冲和带缓冲
- channel 的 send/recv 会阻塞当前协程而不是阻塞线程

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **消息传递** | channel 是 CSP 模型的核心——不共享内存来通信，而是通过通信来共享内存 |
| **并发 = 调度** | 一个线程怎么"同时"执行多个协程？调度才是并发的本质 |
| **状态机（调度器）** | 就绪→运行→阻塞→就绪，调度器就是一个状态机 |
| **封装** | 调用者只看到 spawn、yield、channel，不知道栈切换的细节 |
| **Fail-fast** | 协程 panic 时不能拖垮整个进程 |

## 阶段三：分布式与容错（网络、不确定性、"部分失败"）

---

### 项目 7：Raft 完整实现

**难度：** ⭐⭐⭐⭐☆ | **周期：** 3 周

**需求：**
完整实现 Raft 共识协议——Leader Election + Log Replication + Snapshot。

**要求：**
- 网络层抽象——用可注入故障的 mock 网络做测试
- 至少通过 Jepsen 级别的测试：网络分区、乱序消息、重复消息
- 实现成员变更（单节点加入/离开）
- 实现线性一致读（ReadIndex 或 Lease）

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **状态机（协议级）** | Follower/Candidate/Leader 的状态转移——这是状态机的终极应用 |
| **一致性（线性一致）** | 你实现的每个操作都需要验证是否线性一致 |
| **容错（超时、重试）** | 心跳超时、选举超时、日志复制重试——全部要处理 |
| **幂等** | Leader 重发日志时 follower 必须去重 |
| **隔离** | 一个 follower 挂了不影响其他人的共识 |
| **测试：Jepsen 式** | 注入网络故障同时验证系统正确性——这是你遇到的最严苛测试 |

**为什么这是分水岭：** Raft 要求你同时处理并发、网络、时序、持久化、一致性。这是你第一次真正面对"分布式的不确定性"。

### 项目 8：BitTorrent 客户端

**难度：** ⭐⭐⭐☆☆ | **周期：** 2 周

**需求：**
实现一个 BitTorrent 客户端——能下载一个真实的 torrent 文件，也能做种上传。

**要求：**
- 解析 torrent 文件（bencode 编码）
- 实现 peer wire protocol（握手、消息收发）
- 实现 piece 选择策略（rarest first + random first piece）
- 实现 choke/unchoke 算法（tit-for-tat）
- 支持多 peer 并发下载，piece 组装和完整性验证（SHA1）

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **协议实现** | 从 RFC 规范到二进制协议——这是比 HTTP 更"真实"的协议 |
| **并发：多 peer 管理** | 每个 peer 一个连接，并发下载、上传、心跳 |
| **贪心 + 策略** | Rarest first 是贪心——优先下载全网络最稀少的 piece |
| **数据流** | file → pieces → blocks → 网络包 → 对端 → 组装 |
| **背压** | 你的下载速度和上传速度怎么协调？ |
| **容错** | peer 随时可能断开、发错误数据、恶意行为 |

### 项目 9：基于 LSM 的时序数据库引擎

**难度：** ⭐⭐⭐⭐☆ | **周期：** 3 周

**需求：**
实现一个专用的时序存储引擎。数据模型是 `(metric_name, tags, timestamp) → value`。针对时序场景优化。

**要求：**
- LSM 引擎：memtable → WAL → SSTable → Compaction
- 时序优化：相同 metric+tags 的数据物理相邻存储
- 实现基于时间的 range scan 和聚合查询（min/max/avg over time range）
- 实现保留策略（TTL——自动删除过期数据）

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **LSM 树** | 写优化存储——为什么时序场景天然适合 LSM？ |
| **分层** | Memtable → WAL → Level 0 → Level N，每层职责清晰 |
| **批处理** | 合并多次写入再刷盘；compaction 本身就是批处理 |
| **缓存** | 热点 metric 的 block cache |
| **数据结构：跳表 + 布隆过滤器** | Memtable 用跳表，SSTable 查询用布隆过滤器加速"不存在"判断 |
| **性能：Amdahl** | compaction 策略直接影响查询延迟——找到真正的瓶颈 |

### 项目 10：MQTT Broker 核心

**难度：** ⭐⭐⭐☆☆ | **周期：** 2 周

**需求：**
实现 MQTT 3.1.1 协议的一个功能子集：Connect、Subscribe、Publish、QoS 0/1。

**要求：**
- 基于 TCP 的协议实现——解析 MQTT 二进制包格式
- 主题匹配——支持 `+`（单层通配）和 `#`（多层通配）
- QoS 1 的 at-least-once 语义——消息去重、重发、确认
- Session 持久化——客户端断开后 broker 缓存消息，重连后投递

**核心思想覆盖：**

| 思想 | 锻炼方式 |
|------|---------|
| **协议实现** | MQTT 比 HTTP 更紧凑——变长编码、标志位、二进制协议设计 |
| **消息传递** | Pub/Sub 是消息传递模式的经典形态 |
| **容错：持久化 + 重试** | QoS 1 要求 broker 记住消息直到 ACK |
| **主题匹配算法** | 字典树 + 通配符——这是搜索空间的剪枝 |
| **抽象** | 协议的每一层（帧解析→消息路由→业务逻辑）独立 |

### 项目 11：把 MQTT Broker 拆成微服务

**难度：** ⭐⭐⭐⭐☆ | **周期：** 2 周

**需求：**
将项目 10 的单体 Broker 拆分成三个服务：
- Connection Service（管理 TCP 连接、协议解析）
- Session Service（管理会话状态、消息缓存）
- Route Service（主题匹配、消息路由）

**要求：**
- 服务间通过 RPC 通信（简单实现或用 gRPC）
- 每个服务可以独立部署
- 某个服务挂掉后，整个系统能否继续处理部分请求？
- 你如何保证路由表在多个 Route Service 实例间一致？

**核心思想覆盖（这一题重点训练各种抽象思想）：**

| 思想 | 锻炼方式 |
|------|---------|
| **分层 → 分服务** | 单体中"理所当然"的方法调用变成 RPC——你真的需要这样分吗？ |
| **一致性** | 路由数据在多个实例间用什么一致性模型？强一致还是最终一致？ |
| **降级 + 隔离** | Route Service 挂了，Connection Service 还能做什么？ |
| **重构** | 从单体到微服务——你如何保证行为不变？如何分步迁移？ |
| **复用 vs 耦合** | 服务拆分后，共享的数据模型放哪里？放共享库还是各自定义？ |
| **测试：契约 + 集成** | 服务间的契约是什么？mock 什么不 mock 什么？ |

**为什么要做这个项目：** 它迫使你面对"拆还是不拆"的架构决策。你会在做完之后对微服务的代价有切身体会——这比读十篇文章都管用。

### 项目 12：为一个开源项目提交一个功能 PR

**难度：** ⭐⭐⭐⭐⭐ | **周期：** 3 周

**需求：**
选择一个你常用的开源项目（建议选 NanoMQ 或你熟悉的项目），阅读它的源码，理解架构，然后提交一个被合并的 PR。

**要求：**
- 理解：画出项目的架构图和数据流图
- 贡献：修复一个 bug 或实现一个小功能
- 通过 code review：响应维护者的反馈、修改、再提交
- 遵循项目的编码规范和测试要求

**核心思想覆盖（这一题是全部思想的总和）：**

| 思想 | 锻炼方式 |
|------|---------|
| **读代码 = 模式提取** | 理解别人的设计决策——为什么这样分层？为什么用这个数据结构？ |
| **重构：小步前进** | 你的 PR 只做一件事 |
| **测试** | 项目要求什么样的测试？你如何保证不改坏现有行为？ |
| **Code Review** | 从 review 反馈中学习——这是你最应该珍惜的免费导师 |
| **所有前面的思想** | 状态机、并发、容错、抽象——你会在真实代码中看到它们的影子 |

**为什么这是最后一个：** 前面的 11 个项目都在隔离环境训练单项能力，这个项目让你在真实世界的复杂度中综合运用它们。真实代码没有干净的边界，没有"当然应该这样设计"——你要在现有约束下找到最不坏的选择。

## 软件开发核心思想参考

### 一、计算模型

| 思想 | 核心问题 | 典型场景 |
|------|---------|---------|
| **状态机** | 系统有哪些状态？什么事件触发状态转移？ | 协议实现、UI 交互、订单生命周期、正则匹配 |
| **图灵完备** | 这个抽象是否具备通用计算能力？ | 判断 DSL 的表达边界、理解为什么 YAML 不是编程语言 |
| **可计算性** | 这个问题是否可判定？会不会无限循环？ | 停机问题直觉、递归终止条件验证 |
| **数据流** | 数据从哪来，到哪去，在哪被变换？ | 编译器管线、ETL 管道、响应式编程 |

### 二、并发模型

| 思想 | 核心问题 | 典型实现 |
|------|---------|---------|
| **共享内存 + 锁** | 多个执行单元同时读写同一块数据，如何保证正确？ | Mutex、RWMutex、CAS、volatile |
| **消息传递** | 不共享数据，通过发消息协调。 | Channel (Go)、Actor (Erlang)、MPSC 队列 |
| **并发 vs 并行** | 并发是结构（组织多个任务），并行是执行（同时跑在多个核上） | 单核也能并发 |
| **内存模型** | 一个线程写的数据，另一个线程什么时候能看到？ | happens-before、fence、atomic ordering |

### 三、一致性模型

| 思想 | 核心问题 |
|------|---------|
| **线性一致性** | 写完之后，所有读都必须看到新值（最强） |
| **最终一致性** | 如果不再写入，最终所有读都会看到相同值（最弱） |
| **因果一致性** | 有因果关系的操作按序可见，无因果的可以乱序 |
| **CAP** | 分区发生时，选一致性还是可用性——不是"CP 比 AP 好"，是"这个场景能容忍什么" |

### 四、容错模型

| 思想 | 核心问题 |
|------|---------|
| **Fail-fast** | 尽早暴露问题，不让坏状态蔓延 |
| **幂等** | 同一个操作执行多次和执行一次效果相同——重试的基础 |
| **超时/重试/退避** | 等多久？重试几次？重试间隔怎么增加？ |
| **断路器** | 远程服务不可用时快速失败，不堆积等待 |
| **降级** | 功能不可用时退而求其次，而非整体崩溃 |
| **隔离** | 一个模块的故障不影响其他模块（bulkhead） |

### 五、抽象思想

| 思想 | 核心问题 | 反模式 |
|------|---------|--------|
| **分层** | 上层依赖下层，下层不知道上层存在 | 跨层调用、下层反调上层 |
| **封装** | 暴露什么接口？隐藏什么实现细节？ | 把所有字段都 get/set——那不是封装是仪式感 |
| **复用 vs 耦合** | 抽出一个公共方法，是减少重复还是增加耦合？ | 为两个长得像的函数写一个抽象 |
| **依赖倒置** | 高层模块和低层模块都依赖抽象，而非互相依赖 | 具体类满天飞 |
| **关注点分离** | 一个模块只做一件事——怎么定义"一件事"？ | 切得太细和切得太粗 |

### 六、重构思想

| 思想 | 操作 |
|------|------|
| **小步前进** | 每次只做一种变换，提交，验证，再下一步 |
| **不改变行为** | 重构和加功能分开——一个 PR 只做一件事 |
| **测试先行** | 先有测试——否则重构只是"有组织的破坏" |
| **提取/内联** | 抽方法/变量 vs 把不需要的抽象压回去 |
| **向多态迁移** | 复杂的 if/switch 往策略模式/表驱动改 |
| **简化条件** | 卫语句提前 return，合并重复条件 |

### 七、算法范式

| 范式 | 核心思想 | 标志 |
|------|---------|------|
| **分治** | 大问题拆成相同结构的小问题，合并结果 | 递归树、归并排序 |
| **贪心** | 每步选局部最优，寄希望于全局最优 | 最小生成树、Huffman 编码 |
| **动态规划** | 大问题依赖子问题，缓存子问题结果 | 最优子结构 + 重叠子问题 |
| **搜索/回溯** | 在解空间里系统性尝试，剪掉不可能的分支 | DFS、BFS、分支限界 |
| **滑动窗口** | 两个指针框定范围，单向不回头 | 子串问题、流式统计 |
| **双指针** | 两个遍历位置，各自按条件移动 | 有序数组合并、快慢指针找环 |
| **前缀和/差分** | 区间操作转端点操作 | 批量区间更新 |
| **单调栈/队列** | 维护一个单调序列，可以 O(1) 取最值 | 下一个更大的元素、滑动窗口最大值 |

### 八、测试思想

| 思想 | 回答的问题 |
|------|-----------|
| **等价类** | 输入可以分成哪些等价类？每类只测一个代表？ |
| **边界值** | 0、1、MAX、MAX+1——bug 最爱蹲的地方 |
| **契约测试** | 接口的承诺是什么？前置条件、后置条件、不变量 |
| **Mock 的边界** | mock 什么？不 mock 什么？——只 mock 你拥有的边界 |
| **测试金字塔** | 单元:集成:E2E 应该是大量:少量:极少 |
| **属性测试** | 不测具体值，测"对于任意输入，某性质应始终成立" |

### 九、性能思想

| 思想 | 核心问题 |
|------|---------|
| **缓存** | 一样的数据不重复算——哪一层缓存？什么时候失效？ |
| **惰性** | 不真正用到的就不算 |
| **批处理** | 把多次小操作合并成一次大操作 |
| **预取** | 在用到之前就开始取 |
| **零拷贝** | 数据不变就不搬 |
| **背压** | 下游处理不过来时上游降速，不无脑缓冲 |
| **Amdahl 定律** | 优化非瓶颈部分没意义——先找到最慢的 |
